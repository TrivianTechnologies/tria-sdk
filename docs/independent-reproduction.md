# Independent developer reproduction

Purpose: determine whether a developer outside the build team can install TRIA,
run its reference application, explain its boundaries, and adapt one workflow
using the published materials. This is an onboarding and bounded behavior trial,
not security certification or a human-benefit study.

## Before starting

The coordinator supplies the exact commit to evaluate and this protocol. Use a
fresh checkout and environment. Record your prior involvement with TRIA, operating
system, Python version, start time, and any paid or organizational relationship.
Independence is a disclosed relationship, not a label generated by a test suite.

Python 3.11+ is required. The SQLite reference currently requires POSIX process
locks; use Linux or macOS. A Windows environment needs a compatible Linux runtime,
such as WSL, for this particular storage example. Record setup friction.

The first pass uses synthetic data only, with no model credentials, external calls,
or private documents. Record confusion before asking for help. If help is needed,
continue, but preserve the point of intervention and what assistance was given.

## Install and identify the candidate

```bash
git clone https://github.com/TrivianTechnologies/tria-sdk.git
cd tria-sdk
# Replace REVIEW_COMMIT with the exact commit supplied for this review.
git checkout REVIEW_COMMIT
python -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
git rev-parse HEAD
python -m pytest -q
```

Keep the command output, including any failed installation or test attempt. Do not
silently change dependencies or source to obtain a pass. Record any such change.

## Run the reference application

```bash
python playground/reference_experience.py --output reference-results.json
python examples/governed_assistant.py
python playground/adapter.py
```

With the adapter running, open `http://127.0.0.1:8765/evaluate.html`, run the
five-step experience, inspect each step, and download the report. The command-line
runner returns 0 when all reference checks match and 1 if a check fails. It refuses
to overwrite an existing report. The browser and CLI execute the same runner.

Expected behavior is predeclared:

| Step | Consent | READ permission | TRIA executor entries | Cached comparator entries |
|---|---|---|---|---|
| Initial authorization | Active | Active | 1 | 1 |
| Consent withdrawn | Withdrawn | Active | 0 | 1 |
| Consent renewed | Active | Active | 1 | 1 |
| READ permission withdrawn | Active | Withdrawn | 0 | 1 |
| READ permission restored | Active | Active | 1 | 1 |

Both paths use the same local suggestion function. The comparator deliberately
reuses a cached initially authorized payload without fresh checks. It represents
that failure mode, not all non-TRIA products. The application makes no model or
calendar call. A suggestion of 10:30 AM is a deterministic fixture output.

Verify that every `checks` value is true and that history and its audit survive
SQLite close/reopen. Inspect actual executor entry counts, not just UI labels.
Generated timestamps and IDs vary. Timing samples and report bytes will not match
across runs. Compare semantic outcomes, code fingerprints, versions and checks.
The report contains synthetic projections, not a portable replay bundle or an
authorization token. Full relationship exports use the separate DISCLOSE-gated API.

On the main Playground page, exercise both consent and permission switches, both
withdrawn at once, and restoration. In Contested Reality, inspect with and without
a dispute. Each evaluation constructs a fresh scenario; resetting does not erase
an existing relationship's history. A contested claim is not itself an execution
denial. Stop the adapter and confirm that a failed SDK request reports an error
instead of presenting a simulated result as SDK evidence.

## Reproduce the existing evaluation controls

```bash
python -m evals.unknown_unknown_challenge.run --summary --output diagnostic-results.json
python -m evals.agent_comparison_experiment.harness --summary --output comparison-mock-results.json
```

The first exercises authored synthetic diagnostic controls. The second runs a
mock agent to check the experiment machinery. Neither output is evidence of
improved model reasoning. Live model runs require the separate guarded pilot
protocol and explicit provider/budget decisions.

## Adapt one workflow independently

Using the Quickstart, public API reference, and complete governed application,
change the synthetic scheduling preference to another synthetic preference, and
require a different explicit purpose consistently in grants and requests. Show
one authorized read, one purpose-mismatch denial, and one consent-revoked denial.
Record executor calls. Keep the host's requirement construction explicit.

First attempt the adaptation from documentation and public examples. If you need
to read SDK implementation code or receive assistance, record where and why.
Do not count a source-assisted completion as a docs-only success.

## Return the evidence

Return the completed [report template](reproduction-report-template.md), the
candidate commit, command logs, original result JSON files, your adaptation patch,
and any screenshots that clarify discrepancies. Review artifacts for local paths
or personal information before sharing. Submit ordinary bugs through repository
issues; follow SECURITY.md for security-sensitive findings.

Record results as reproduced, reproduced with assistance, failed, or not assessed.
Keep failures and unfinished work. Separate installation success, semantic
reproduction, adaptation success, and usability feedback. A later pilot with actual
participants should define its own consent, workflow, measures and success criteria.
